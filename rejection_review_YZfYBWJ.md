# Reject

The submission contains useful observations about numerical reference behavior on GB10 and is substantively relevant to correctness-preserving GPU optimization. The profiler-backed dispatch map, precision-flag comparisons, and retained candidate records could support a bounded measurement paper. This version nevertheless overstates the connection between engine dispatch and its headline admission experiment, mixes incompatible delivery conventions, and leaves consequential contradictions in its scientific interpretation.

Independent CPU recalculation from the retained records confirms the $672$ default-reference labels, admissible-arm counts $128/203/293/672$, and frontier changes $10/24/30$, including the stated strict-median/tie splits. It also confirms the four crossed selector-regret values $3.49614/3.92334/3.59633/4.03814\%$, the $26$ reduction-label changes between input draws, and class agreement across the $34$ recorded tuple-surface runs. These checks validate record-level arithmetic. I inspected the relevant measurement code but did not reproduce the GPU experiments.

1. **The central engine-class attribution exceeds the matched evidence.** The abstract, §1.7, §9.5 and Appendix A.5 attribute $11/56$ changes to an “engine-class swap alone,” specifically default dispatch to an fp32-SIMT route. However, `r41_gate_stability.py` changes `cudnn.allow_tf32`, recomputes references, and retains pass maps; it neither profiles nor records the engines used for these rows. This establishes an intervention on the reference precision configuration with fixed candidate outputs. It does not establish the claimed engine transitions on that population.

   The distinction matters because the paper's own Table 1 shows that disabling TF32 can leave Winograd unchanged, replace a tensor-op route with SIMT, or replace it with Winograd (B03). The table cannot supply the missing labels for the swap population: §9.5 acknowledges that only two frontier tuples match Table 1. Thus the asserted SIMT mechanism and the admitted absence of a matched engine-class analysis coexist in the same novelty argument. Report the supported precision-configuration intervention, or supply paired engine observations for the relevant rows and distinguish changed precision from changed algorithm family. The observed reference dependence remains useful without assigning an unmeasured mechanism.

2. **The headline swap counts do not use the paper's own admissible-delivery convention.** In `r41_gate_stability.py`, `gate_from_pass` retains `torch` unconditionally as fallback and includes it unconditionally in the oracle. Its `admissible` list contains only passing hand kernels. Consequently, the headline $21/56$ and $11/56$ count changes in selected arm identity under this convention, while $48/56$ and $15/56$ count changes in the hand-only admissible set.

   Recalculation from the same pass maps gives:

   | Reference change | Selected-arm changes | Selected arms failing the new check | Delivery-status changes after enforcing admission | Changes in the full admissible set |
   |---|---:|---:|---:|---:|
   | Default to TF32-disabled | 11 | 24 | 35 | 35 |
   | Default to fp64 anchor | 21 | 31 | 52 | 52 |

   The $21$ and $11$ arm-to-arm transitions are real within the stored predicates. They are not the complete delivery-status result. Sections 3.4 and 4.2 already recognize the $21+31=52$ decomposition, but the abstract and novelty argument return to the earlier convention without identifying it. Use one explicit policy and distinguish selection, admissible delivery, no delivery, and hand-only versus full-pool membership throughout. This changes the scientific meaning of the reported effect, rather than merely its wording.

3. **Evaluator-exact verification is incomplete for the reference-swap result.** At KernelBench revision `423217d`, `torch.allclose(output, output_new, ...)` scales the relative term by the candidate. The swap producer instead uses

   $$
   \max_i\left(|Y_i-R_i|-(10^{-4}+10^{-4}|R_i|)\right)\leq 0.
   $$

   Section 5.3's statement that every shipped harness is evaluator-exact is therefore false. The cited $0/560$ disagreement audit in `f24_verify.py` compares hand-arm labels only against the default reference; it does not establish equivalence for the TF32-disabled and fp64 swap checks. The later candidate-scaled ratio recorder likewise concerns the default reference. The swap records retain Boolean verdicts rather than the outputs or both directional ratios needed to resolve this independently.

   This finding does not establish that the swapped-reference labels would change. It establishes that their advertised evaluator-exact status is unsupported. Recompute or certify both directions on the swapped references, including the baseline arms, and retain sufficient numerical evidence. Alternatively, explicitly describe this experiment as using a different predicate and limit its conclusions accordingly.

4. **The main text still gives materially conflicting interpretations of what the certificate establishes.** Section 4.1 correctly separates reference accuracy from candidate agreement and supplies counterexamples. Yet §1.6 says that near-zero reference exceedance makes the reference usable and the speed ratio meaningful, while §4.4 suggests that the remaining in-budget reference elements explain why a bulk-error row can be evaluated. Candidate agreement can be evaluated even when every reference element exceeds the anchor budget. Reference exceedance alone supplies neither a candidate-accuracy guarantee nor an application-level justification for a speed comparison.

   Similarly, §4.5 correctly describes Spearman correlation as rank agreement, but §9.3 calls it calibration. Sections 2.5 and 7.2 correctly limit the $0.604$ result to a nearest-centroid classifier, while §8.4 concludes that admission must remain measured per shape because those coordinates do not predict the engine. Failure of that classifier does not establish that requirement. These are conflicting operational conclusions about the central contribution, not minor terminology issues.

   Consolidate the argument around the defined reference diagnostic, the paired reference intervention, and its admission consequences. Move the repeated repair history, audit declarations, superseded interpretations and secondary experiment narratives out of the main argument. State each population, predicate and supported inference once. A compact figure connecting reference configuration, observed engine, reference deviation and candidate verdict would help expose which links are measured and which remain hypotheses.

The novelty is narrow but potentially meaningful. Du et al. [9] already report official references violating their tolerance against fp64; Zhang et al. [10], especially Appendix J, already demonstrate tolerance-dependent correctness and performance selection; Barabasz et al. [7] analyze Winograd rounding error; and PyTorch's documentation [8] explains shape-dependent numerical behavior and TF32 controls. The supplied same-problem publication index contains no additional published comparator. The checked literature does not establish precedence for this exact GB10 dispatch table, so a clear, sound account of that measurement need not solve a broader benchmark-wide problem. However, the general reference-dependence premise and a per-shape presentation of tolerance sensitivity do not by themselves supply a new mechanism. The unsupported attribution in finding 1 is therefore particularly consequential to the distinction claimed in §9.5.

The declared single-device scope, designed shape grids, unlocked clocks and limited input draws are acceptable limitations for a descriptive contribution. The informative abstract should define $\rho$ and replace unexplained “class-cells” with ordinary language. Correct reference [9]'s title to *Measuring the Checker: Mutation Analysis for GPU-Kernel Benchmark Oracles*, complete [11]'s bibliographic information, and consistently delimit mathematical expressions. Those presentation repairs are minor; acceptance requires resolving the substantive evidence and interpretation issues above.
