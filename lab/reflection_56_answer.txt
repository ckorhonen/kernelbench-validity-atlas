NEW REFLECTION — negative evidence into direction.

The impossibility argument I should examine is one I have been carrying since A7 and have never stated as an impossibility: **the engine class is not recoverable from the conv parameters.** A7 named the engines (winograd_nonfused, cutlass tensorop TF32) and A8 measured that class predictability from (k, s, d, C, output extent) is 0.604 against a 0.5625 majority. What that establishes is narrow and I have been treating it as broad. It establishes that on my 48-shape lattice, a nearest-centroid classifier over those coordinates cannot recover the class. It does not establish that the class is unrecoverable — the failure mechanism is that the dispatch boundary sits in a coordinate I did not supply, not that no coordinate exists.

What remains possible, and is cheap: the class is a property of the cudnn heuristic's own inputs. The heuristic sees (N, C, H, W, K, R, S, stride, pad, dilation, dtype, layout, and the arch's resource budget) and picks an engine deterministically. My lattice held most of those fixed and varied a few, so the classifier was asked to infer a high-dimensional decision from a low-dimensional projection. The escaping route is not a better classifier over the same projection; it is to enumerate the heuristic's actual inputs and measure which ones flip the engine, which is what A7 did for precision flags and A6f did for K. I have already run two of those single-coordinate sweeps and both flipped it (C at fixed output extent; precision flag). So the honest restatement is: the class is a deterministic function of the heuristic's full input tuple, and predictability 0.604 is a statement about my projection, not about the class.

Would strengthening it change a decision? Yes, one, and it is the decision §4 currently makes. If the class is a deterministic function of a tuple I can enumerate, then the "measured-per-shape cost" framing for admission is unnecessarily pessimistic: a reader who supplies the tuple gets the class without measuring, and frac_over follows from it. That would upgrade admission from a per-shape measurement to a dispatch over an enumerated tuple — a strictly better deliverable, and exactly the kind of claim §4 has been careful not to make. If instead the tuple does not determine the class (heuristic has internal state, or ties broken by timing), then per-shape measurement is the honest floor and §4 stands.

The discriminating test I will run next, pre-registered: for a fixed shape, vary only the tuple coordinates the classifier never saw — stride, pad, dilation, layout (NCHW vs NHWC), and batch — and record whether the engine class changes while (k, s, d, C, output extent) is held fixed. If the class flips on any of those, the projection argument is confirmed and the class is recoverable from an enumerated tuple. If it never flips across all of them, the class is genuinely a function of my measured coordinates and 0.604 is a real unpredictability result, which strengthens §4's pessimism rather than weakening it. Either branch is publishable and neither requires new hardware.

What this changes in the plan: §4.5's class-predictability sentence currently reads as a negative result. Under this reading it is a scoping result, and I will not touch the sentence until the tuple test returns, because the paper is under review and the edit needs a measured reason. The test is one GPU leg, roughly the cost of A7.
