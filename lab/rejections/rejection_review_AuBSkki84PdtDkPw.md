# Reject

The GB10 measurements could support a useful, narrowly scoped paper on numerical reference behavior in KernelBench. The reported dependence on convolution dispatch, the seed-sensitive matmul crossing, and the LayerNorm example where a candidate is closer to an fp64 anchor but fails reference agreement are relevant to correctness-preserving optimization. However, this version still contains an invalid layout experiment, unsupported claims about admission and dispatch predictability, and incorrect accounting of a correctness-preserving selector. Its main contribution also remains materially unclear because incompatible interpretations survive alongside their corrections.

I inspected the measurement and analysis code and independently recomputed selected quantities from retained records; I did not reproduce GPU experiments. The stored compression predictions reproduce the reported multiplicative errors, and the six composition ratios reproduce approximately $0.981,1.507,1.537,1.000,1.971,2.480$. The retained LayerNorm records support the stated contrast at offset 1000. These checks support specific empirical observations, not the broader certificate and deployment conclusions.

1. **The central interpretation still conflates reference accuracy with candidate admission.** Section 4.1 correctly distinguishes benchmark agreement, anchor accuracy, and a separately declared application contract. Its scalar counterexample also correctly shows that a reference with every element outside its anchor budget can have a candidate that passes both comparisons. But §4.4 nevertheless states that a speedup at a reference with `frac_over = 0.77` is “a ratio between two arms that both miss the contract.” That conclusion does not follow from the reference statistic. Section 2.4 likewise calls such rows “bulk-inadmissible” and directs the reader to report the pair rather than a ratio, while §1.4 and §4.5 repeatedly describe bulk-reference classification as an admission result.

   This is a substantive contradiction in the proposed certificate's purpose. A candidate identical to the recorded reference passes benchmark agreement regardless of that reference's distance from fp64. Conversely, reference–anchor agreement does not certify candidate–anchor agreement. The official evaluator at revision `423217d` confirms the candidate-versus-reference comparison and fp32 tolerance $10^{-4}$; it does not impose an fp64 accuracy contract. Use separate notation and results columns for these predicates throughout, and remove implications that the measurements do not establish. A high reference error can motivate an additional accuracy requirement, but cannot retrospectively invalidate an otherwise valid benchmark speedup. Claims that “no loosening rescues” a bulk-error reference also need a specified application tolerance, not an undefined judgment about realistic loosening.

2. **The claimed NHWC intervention does not run convolution in that layout.** In `kernels/tuple_test.py`, the NHWC branch forms an NHWC temporary, then applies `permute(0, 3, 1, 2).contiguous()` before passing `x_run` to `F.conv2d`. That restores ordinary contiguous NCHW storage. The recorded `x_strides` describe the intermediate `x_nhwc`, not the actual convolution input. Consequently, §2.5's layout-invariance claim and its description of a real NHWC test are unsupported. Run a genuine channels-last input through convolution, record the strides of the tensors actually passed to both flag settings, and regenerate the affected evidence. This requires a corrected experiment, not a relabeling of the current strides.

3. **The dispatch and compression experiments do not establish the stated negative conclusions.** Counting six class changes between consecutive entries of a manually ordered tuple list does not rule out a simple threshold boundary. On the supplied nine rows, the observed classes are already consistent with the simple rule “W when stride and dilation both equal one; T otherwise.” That is a description of these rows, not a proposed general law, but it directly shows why their ordering cannot establish the claimed absence of a simple boundary. The sentence in §4.5 that the tuple test “rules out a threshold in the coordinates it varied” is therefore unsupported.

   Likewise, the $0.604$ nearest-centroid accuracy establishes the performance of that classifier on that feature set and lattice. It does not establish that class identification requires profiling, or that continuous derived-coordinate models fail generally. Several passages acknowledge this limitation, but §1.4, §4.5 and §7.2 still draw the broader conclusion. The compression targets are reference-error magnitude and the event `frac_over > 0.5`; neither is candidate admission. No admission-prediction experiment supports the contrast “magnitude compresses, admission does not.” Report the actual prediction targets and restrict negative findings to the evaluated models. Also resolve §7.2's claim that the geometry-only magnitude model uses one coordinate: the shipped `feats` functions supply four coordinates to that model. A profiler pass identifies an engine; it does not by itself obtain the exact anchor-error pair or a candidate-level admissible set.

4. **The all-row deployment cost is not the cost of the stated fallback policy.** Sections 6.2–6.4 describe $+3.53\%$ as the cost over all 24 reduction rows with torch executed on every failing row. However, `write_analysis` in `s56_heldout_contract.py` always computes regret from the original gate arm's `t_ms`, including when `pass_full` is false. It records a fallback name without substituting its timing. Independently recomputing from `s56_heldout_contract.json` gives:

   | Accounting population/policy | Mean excess execution time | SE across rows |
   |---|---:|---:|
   | Original gate, including failed deliveries, 24 rows | $3.5304\%$ | $1.3745$ percentage points |
   | Substitute recorded torch timings on failures, 24 rows | $3.4961\%$ | $1.3712$ percentage points |
   | Nine passing hand deliveries | $0.8613\%$ | $0.3700$ percentage points |

   The numerical difference between the first two means is small; the policy mismatch is the important defect. Neither estimate includes the runtime work needed to discover failures. Section 6.4 says D1 pays for checks and chooses the cheapest passing arm, whereas the reported statistic evaluates the old gate against that cheapest arm. These are different policies: selecting the measured cheapest passing arm has zero selection regret by construction before checking and selection overhead. Specify which policy is evaluated, how it learns correctness on fresh inputs, whether timings are already known, and how checking costs are charged or amortized. The $1.37$ SE attached to the nine-row result in §6.3 also belongs to the 24-row population. These SEs describe variation across designed shapes, not uncertainty from repeated timing trials.

5. **Clarity is independently below the acceptance threshold.** The problem is not merely length or technical depth. Section 1.2 organizes the argument around previous rejection rounds; subsequent sections repeatedly interleave old numbers, retractions, replacement interpretations, experiment identifiers and schema records. A reader must reconstruct the current result from that history. Section 4 calls the certificate the primary contribution, §7.4 says “The certificate is the contribution,” and §9 says it is not a contribution on its own. The global “never eager PyTorch” comparator statement is contradicted by the later eager-only pool. These inconsistencies make it difficult to determine which scientific claim and policy the evidence is meant to support.

   Rewrite the main text around the final research question, definitions, measurement method, supported findings and limitations. Move review history, obsolete results, audit counts and repetitive schema entries to appendices. Explain each current arm and population before comparing them. A dispatch map and a matmul pass-fraction plot would communicate the findings more clearly than repeated experiment narratives; retain the numerical records alongside them. The metadata abstract should summarize those final findings without implying that bulk-reference classification is an admission test.

6. **Reproducibility assurances exceed the delivered implementation.** The package is substantially more useful than a collection of prose summaries, but several producers, including `a7b_precision_policy.py`, `a9_compose.py` and `tuple_test.py`, still write under `kernels/results/`, whereas the supplied records are under the sibling `results/` directory. Thus the claimed shared resolver is not applied throughout. The README also retains obsolete held-out results, including 11/12 passing reduction deliveries and bias-contaminated convolution ratios. Provide one authoritative set of run instructions and final results. Consistency auditors cannot establish that an experiment implemented its described intervention or that a stored statistic measures the stated policy; the layout and fallback defects illustrate that limitation.

The novelty claim should remain an empirical GB10 characterization. KernelBench [1] already defines correctness relative to reference outputs and discusses randomized checking. Barabasz et al. [7] analyze Winograd rounding error, transform conditioning and methods to improve accuracy. PyTorch's official documentation [8] explicitly describes order-dependent arithmetic, differences between batched and individual computations, and the TF32 precision tradeoff and controls. The general principles are therefore established; the potentially new contribution is the particular dispatch-dependent error map and its concrete consequences on this device. I found no basis in this focused comparison to reject those measurements for substantial publication overlap. Informal posts can appropriately receive attribution for borrowed ideas without establishing publication precedence. Single-device scope and useful partial progress are acceptable here; the rejection rests on the unsupported interpretation, defective experiment and materially unclear final argument.
