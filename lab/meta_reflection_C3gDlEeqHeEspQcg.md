**The strongest success I have to examine is my own tuple-surface measurement, and I will separate what made it work from what only happened to be true.** The result: engine class is a deterministic function of the declared tuple across 17 cells and two repeats (34/34 agreement); real channels_last dispatches a TF32 tensorop engine at rho 429.4 while allow_tf32=False drops the same cell to fp32 SIMT at rho 0.239 and bit-inequal; pad-2 reproduces the round-9 reviewer's stored 12.8024 exactly; the fp64 anchor lands in class O (implicit_convolve_dgemm) in every cell.

Essential structure, four parts. First, it treated the vendor library's engine choice as an observable rather than an assumption — the profiler named the engines (winograd_nonfused, cutlass tensorop_s1688 TF32, implicit_convolve_dgemm), so "reference error" stopped being a scalar and became a named object. Second, every class assignment had a discriminator that could have failed: flag-off removing 96.4-99.9% of the deviation is what licenses calling a cell TF32, and it did fail for winograd cells earlier, which is why A6f's "invisible to every precision flag" got retracted. Third, the intervention executed rather than a proxy for it — the NHWC row that "reproduced NCHW to the digit" was the same layout twice, so I now require the intervention to be performed on the object it names. Fourth, the output was framed in the coordinates a dispatcher actually has (layout, stride, pad, dilation, C, H, W), which is why the deliverable is a lookup table with a validity domain instead of a fitted curve.

Incidental: the particular 17 cells, the rho magnitudes themselves, the choice of two repeats, and the version pin (cudnn 92400, torch 2.14.1+cu130). Any of those could change without touching the structural claim.

**What prevents the mechanism from extending.** Three obstacles, and they are the honest content of the paper's limitation section. (1) It is an enumeration, so its reach stops at measured cells; class steps depend on depth and extent, so interpolation between cells is a guess until tested — exactly what the deferred out-of-family predictor would settle. (2) Determinism was measured across two repeats inside one process, which cannot distinguish "deterministic function of the tuple" from "cached decision from the first call". A cudnn heuristic cache makes those two statements identical from the inside. (3) Engine class is a vendor decision under a workspace budget, so the map is a snapshot of one library build on one device, not a law about convolution.

**Substantive extension.** Attack obstacle (2) directly, because it is the one that decides whether the certificate is a law or a memo: re-measure the 17 cells in fresh processes with the heuristic cache cold, with cudnn benchmark mode on and off, with deterministic algorithms on and off, and with a constrained workspace budget as an added coordinate. The question is whether the class label is invariant to all of those at fixed tuple. If it is, the claim upgrades from "deterministic within a process" to "deterministic function of declared tuple plus workspace budget", which is a coordinate a real dispatcher can consume; if any cell flips at fixed tuple and fixed budget, the categorical claim narrows to per-process caching and Table 1 becomes a measurement rather than a map. This is one GPU block, no new kernels, and it uses the same 17 cells so it is directly comparable.
